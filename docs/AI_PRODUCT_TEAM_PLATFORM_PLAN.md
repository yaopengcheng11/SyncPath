# SyncPath：AI 产品团队工作平台规划

> 版本：v0.1
> 目标读者：产品负责人、AI 产品经理、设计/研究、研发、算法/数据、管理层
> 本文定位：产品方向、信息架构、功能优先级、技术架构和迁移路线的统一基线

执行细化见 [开发计划、框架设计与验收标准](SYNCPATH_DEVELOPMENT_FRAMEWORK_ACCEPTANCE.md)。后续版本范围、排期、任务依赖和验收以该文档为准；本文件保留产品长期方向。

## 1. 结论

SyncPath 应从“项目时间轴 + 周志工具”升级为一套面向 AI 产品团队的 **产品决策与交付中枢**。

它解决的核心问题不是任务有没有完成，而是：

1. 我们为什么做这件事？依据来自哪些用户、数据和业务目标？
2. AI 能力是否真的可用？用什么模型、数据集和评测标准验证过？
3. 产品判断如何转化成规格、实验和研发交付？
4. 上线结果是否验证了原始假设？下一步应该继续、调整还是停止？

建议围绕以下闭环构建产品：

`信号收集 → 洞察归纳 → 机会判断 → 优先级决策 → 产品规格 → AI 实验与评测 → 研发交付 → 发布观测 → 复盘学习`

当前 SyncPath 的时间轴和日志可以保留，但应成为“交付与复盘”视图，而不是整个产品的中心数据模型。

## 2. 产品定位

### 2.1 一句话定位

SyncPath 是 AI 产品团队用于连接用户证据、产品决策、AI 实验和研发交付的协作平台。

### 2.2 差异化方向

市场上的常见工具各自擅长一段流程：

- Jira Product Discovery 擅长收集想法、优先级和路线图。
- Productboard 擅长反馈归纳、洞察与功能机会关联。
- Linear 擅长把客户请求连接到工程交付，并开始把代码上下文提供给产品团队。
- Notion 擅长知识组织、跨数据源搜索和通用 AI 助手。

SyncPath 不适合在第一阶段与它们比“更多字段”或“更自由的文档”。更有价值的差异是：

- 面向 AI 产品，而不是泛项目管理。
- 以“证据链”和“决策链”为核心，而不是只管理任务。
- 将模型、Prompt、数据集、实验、评测、成本和风险纳入产品过程。
- AI 输出必须带来源、可审核、可回滚，并能沉淀为团队资产。
- 同时服务产品、算法、研发、设计和管理层，各角色看到同一事实的不同视图。

### 2.3 不做什么

首期不建议把 SyncPath 做成：

- 通用文档编辑器；
- 完整研发 Issue 管理器；
- 替代 GitHub、Linear 或 Jira 的工程执行系统；
- 完整 MLOps、模型训练或部署平台；
- 无边界的聊天机器人集合。

SyncPath 应保存产品决策和 AI 产品上下文，并通过集成连接专业执行工具。

## 3. 用户画像与核心任务

### 3.1 主用户：AI 产品经理

典型目标：

- 把访谈、工单、销售反馈、埋点和市场信息整理成可验证机会；
- 快速形成 PRD、用户故事、验收标准和风险清单；
- 与算法团队明确模型能力边界、评测集和上线阈值；
- 与研发同步依赖、范围、进度和阻塞；
- 向管理层解释优先级、投入和结果；
- 在版本迭代之间保留“为什么这么决定”的上下文。

主要痛点：信息散落、AI 结论不可追溯、PRD 与实际实现脱节、模型效果缺少统一标准、上线后复盘断链。

### 3.2 协作用户

| 角色 | 关心的问题 | 默认工作台 |
|---|---|---|
| 产品负责人 | 组合投入是否符合战略，哪些机会值得继续 | Portfolio / Decision Review |
| AI 产品经理 | 用户证据、方案、规格、实验和上线结果是否连贯 | Product Workspace |
| 用户研究/设计 | 问题是否真实，方案是否被验证 | Insights / Discovery |
| 算法/数据 | 数据集、模型、Prompt、评测和阈值是什么 | AI Lab / Evaluation |
| 研发/测试 | 范围、依赖、验收标准和风险是否明确 | Delivery / Release |
| 销售/客户成功 | 客户声音是否被记录和响应 | Feedback Portal |
| 管理层/访客 | 为什么做、进度如何、结果怎样 | Read-only Briefing |

### 3.3 权限角色

建议采用工作区级角色加项目级角色：

- Workspace Owner：组织、计费、安全和集成；
- Admin：成员、模板、字段、AI 策略；
- Product Lead：产品组合和决策审批；
- Editor：创建和编辑产品内容；
- Contributor：提交反馈、评论、更新分配内容；
- Viewer：只读访问；
- External Guest：只能访问明确分享的项目或门户。

## 4. 核心信息架构

### 4.1 一级导航

1. **Home**：个人待办、近期决策、风险、AI 任务和关注项目。
2. **Inbox**：所有待分类信号，包括反馈、访谈、工单、会议记录和外部导入。
3. **Discovery**：洞察、客户、机会、假设、竞品和研究计划。
4. **Roadmap**：产品方向、计划项、依赖、时间轴和情景方案。
5. **Specs**：产品 Brief、PRD、用户故事、验收标准和决策记录。
6. **AI Lab**：模型/Prompt 方案、数据集、实验、评测、成本和安全风险。
7. **Delivery**：与 Jira/Linear/GitHub 同步的实施状态、发布和阻塞。
8. **Analytics**：目标指标、实验结果、质量趋势和产品健康度。
9. **Knowledge**：可搜索的团队产品知识与 AI 问答。
10. **Settings**：成员、权限、模板、字段、集成、AI 模型和预算。

### 4.2 核心对象

| 对象 | 作用 | 必须关联的上下文 |
|---|---|---|
| Signal | 原始信号：反馈、访谈、工单、数据异常 | 来源、客户、时间、原文 |
| Insight | 从多个信号提炼的稳定洞察 | 证据、置信度、影响人群 |
| Opportunity | 值得解决的问题或产品机会 | 洞察、目标、价值、风险 |
| Initiative | 团队决定投入的产品计划 | 机会、负责人、周期、优先级 |
| Spec | 可评审的产品方案 | Initiative、范围、验收、决策 |
| AI Experiment | 对模型/Prompt/检索/流程的实验 | 假设、版本、数据集、指标 |
| Evaluation | 自动或人工评测结果 | 实验、样本、评分、失败案例 |
| Delivery Link | 外部研发任务映射 | Spec、Issue/PR、状态、负责人 |
| Release | 一次可识别的产品发布 | Initiative、变更、回滚、指标 |
| Metric | 产品或 AI 质量指标 | 目标、当前值、数据源、阈值 |
| Decision | 关键选择及其理由 | 选项、证据、审批人、日期 |
| Review | 阶段评审与复盘 | 结论、后续动作、知识沉淀 |

最重要的产品关系是：

`Signal → Insight → Opportunity → Initiative → Spec → Experiment → Delivery → Release → Metric → Review`

所有 AI 生成内容必须能指回这条链上的来源对象。

## 5. 功能规划

### 5.1 P0：先把产品变成可靠的团队系统

这是前后端分离的基础阶段，目标是替换浏览器本地存储和临时 P2P 同步。

- 工作区、团队、项目和成员管理；
- 邮箱密码登录，预留 OAuth/OIDC/SSO；
- 项目级权限和只读分享；
- 服务端持久化、自动保存和乐观更新；
- 操作历史、撤销恢复和审计日志；
- 评论、@成员、通知中心；
- 附件和对象级链接；
- 统一搜索；
- 当前 JSON 数据导入迁移；
- 现有时间轴、日志和节假日功能迁移到新 API；
- 修复并统一根目录与 `src/` 两套前端代码。

验收标准：两名用户在不同设备登录同一工作区，能安全地查看和协作编辑同一项目，刷新后数据不丢失，并能查看关键变更来源。

### 5.2 P1：专业产品管理核心

#### 信号与洞察 Inbox

- 手动录入、CSV 导入、邮件转发和 Webhook；
- Slack/飞书/企业微信、客服和表单入口逐步接入；
- 原文、来源链接、客户、标签、产品区域和情绪；
- 去重、合并和批量归类；
- AI 摘要、主题聚类和关联机会建议；
- AI 结论显示引用片段，用户确认后才进入正式洞察。

#### Opportunity 工作台

- 问题陈述、目标用户、当前替代方案、影响范围；
- 关联洞察和反证；
- 假设、置信度和验证计划；
- RICE、ICE、WSJF、自定义加权评分；
- “评分依据”必须可展开，不只显示一个总分；
- 机会状态：发现、验证中、已验证、承诺、拒绝、归档。

#### Roadmap 2.0

- Now / Next / Later；
- 季度、月份、周粒度时间轴；
- Outcome、主题、产品线和团队视图；
- 依赖、里程碑、风险和置信度；
- 基线与当前计划对比；
- 情景规划：保守、基准、激进方案；
- 管理层只读视图和外部分享；
- 当前 SyncPath 时间轴升级为 Roadmap 的一个视图。

#### Spec Studio

- Brief、PRD、实验方案、发布说明等模板；
- 问题、目标、非目标、用户流程、边界、验收标准；
- 需求与洞察、决策、外部 Issue 双向关联；
- 字段级评论、审批和版本对比；
- AI 草拟、补漏和一致性检查；
- “待确认事实”和“AI 推断”使用不同状态展示。

### 5.3 P2：AI 产品团队专属能力

#### AI Lab

- 模型供应商、模型版本和调用参数登记；
- System Prompt、模板、工具和知识源版本化；
- 数据集、测试样本、标签和敏感级别；
- 实验对比：模型、Prompt、RAG、Agent 流程 A/B；
- 自动指标与人工评分结合；
- 失败案例库和回归测试集；
- 质量、延迟、Token、成本四维对比；
- 上线阈值、降级策略、人工接管和回滚方案；
- 模型或 Prompt 变更对产品规格和评测的影响提示。

#### AI 产品风险清单

每个 AI Initiative 默认包含：

- 幻觉与事实错误；
- 偏见和不公平；
- 隐私和敏感信息；
- Prompt Injection 与越权工具调用；
- 内容安全；
- 可解释性与来源；
- 人工审核边界；
- 成本失控；
- 供应商和模型版本漂移；
- 降级、熔断和退出机制。

#### AI Copilot

Copilot 不应只是右下角聊天框。建议嵌入具体任务：

- 从反馈生成候选洞察；
- 从洞察生成问题陈述和验证计划；
- 从 Initiative 生成 Brief/PRD 初稿；
- 检查 PRD 是否缺少验收标准、风险或证据；
- 把会议记录转成决策、行动项和待验证假设；
- 查询“为什么做这个功能”，回答时提供来源；
- 比较两个方案并列出证据、假设和未知项；
- 根据失败案例建议补充评测集；
- 生成周报、版本说明和管理层摘要；
- 发现路线图、规格和研发状态之间的不一致。

所有 AI 动作采用“建议 → 人工审核 → 写入”的模式。自动写入应由管理员按动作类型单独授权。

### 5.4 P3：交付与集成

- GitHub/GitLab：Issue、PR、Commit、Release；
- Linear/Jira：项目、Issue、状态、负责人、周期；
- Slack/飞书/企业微信：反馈采集、通知和审批；
- Figma：设计稿和版本链接；
- 数据平台：产品指标或实验结果；
- Webhook、REST API 和服务账号；
- Integration Health：同步延迟、错误、权限和上次成功时间。

关键原则：外部工程系统保留执行事实，SyncPath 保存产品意图、证据、规格和跨系统关系，避免双向同步所有字段。

### 5.5 P4：组织级能力

- SAML/OIDC SSO 和 SCIM；
- 自定义角色和字段权限；
- 审计日志导出、数据保留和删除策略；
- 多工作区和产品组合管理；
- 模板中心与组织方法论；
- AI 模型白名单、数据策略和预算控制；
- 用量、成本和 AI 质量管理后台；
- 私有化或指定区域部署选项；
- 数据导出和供应商退出能力。

## 6. 前后端分离目标架构

### 6.1 推荐形态

第一阶段采用 **模块化单体后端 + 独立 Worker**，避免过早拆微服务。

| 层 | 推荐方案 | 说明 |
|---|---|---|
| Web 前端 | React + Vite + TypeScript | 延续现有技术，降低迁移成本 |
| 路由/请求 | TanStack Router + TanStack Query | URL 状态、缓存、乐观更新 |
| UI 状态 | Zustand 或局部 React 状态 | 只存界面状态，不复制服务端数据 |
| API 服务 | NestJS + Fastify | TypeScript 全栈、模块边界和 OpenAPI |
| API 协议 | REST/OpenAPI；实时部分 WebSocket | 自动生成前端客户端和契约测试 |
| 主数据库 | PostgreSQL | 关系、事务、审计和多租户基础 |
| ORM | Prisma 或 Drizzle | 团队择一，不同时混用 |
| 语义检索 | PostgreSQL + pgvector | 早期减少独立向量库复杂度 |
| 缓存/队列 | Redis + BullMQ | AI 任务、导入、通知、异步同步 |
| 文件 | S3 兼容对象存储 | 附件、导入文件和导出产物 |
| 实时协作 | WebSocket；富文本按需使用 Yjs | 不再通过 WebRTC 同步整个 AppState |
| AI Gateway | 后端模型适配层 | 模型路由、结构化输出、成本与审计 |
| 可观测性 | OpenTelemetry + 日志/指标/错误平台 | 串联用户操作、API 和 AI 调用 |

### 6.2 仓库建议

```text
SyncPath/
  apps/
    web/                 # React SPA
    api/                 # NestJS API
    worker/              # AI、集成、通知任务
  packages/
    domain/              # 领域类型和纯业务规则
    api-client/          # OpenAPI 生成客户端
    ui/                  # 共享设计系统
    config/              # ESLint、TS、测试配置
  prisma/                # Schema 和 migration（若选择 Prisma）
  docs/
  infra/
```

可以采用 npm/pnpm workspace。是否引入 Turborepo 取决于构建规模；首期不是必要条件。

### 6.3 后端模块边界

- Identity：用户、登录、会话、SSO；
- Workspace：组织、成员、团队、权限；
- Product：项目、产品区域和组合；
- Discovery：Signal、Insight、Customer、Opportunity；
- Planning：Initiative、Roadmap、Milestone、Dependency；
- Specification：文档、模板、版本、审批；
- AI Lab：模型配置、Prompt、Dataset、Experiment、Evaluation；
- Delivery：外部 Issue、PR、Release 映射；
- Collaboration：评论、通知、活动和实时事件；
- Search：全文、语义检索和权限过滤；
- Integration：OAuth、Webhook、同步任务；
- AI Gateway：模型调用、Prompt 版本、用量、来源和策略；
- Audit：审计事件和导出。

模块之间先通过应用服务和领域事件协作。只有当某个模块出现独立扩缩容或合规边界时，再拆成服务。

## 7. 数据与权限设计

### 7.1 多租户

所有业务表必须包含 `workspace_id`，查询默认附带租户范围。高敏感对象额外保存访问策略。建议使用应用层授权并结合 PostgreSQL Row Level Security 做纵深保护。

### 7.2 权限模型

采用 RBAC + 对象关系授权：

- RBAC 决定用户在工作区内能做什么；
- 项目成员关系决定能访问哪些项目；
- 对象继承项目权限；
- 外部分享使用单独的 Share Link 策略；
- AI 检索必须使用与原始内容相同的权限过滤。

### 7.3 审计与版本

以下动作必须进入不可随普通编辑删除的审计日志：

- 登录、成员和权限变更；
- 关键对象创建、删除和恢复；
- 路线图和规格审批；
- AI 生成内容被接受、修改或拒绝；
- 模型、Prompt、数据源和安全策略变更；
- 外部集成授权和数据导出。

Spec、Decision、Prompt 和 Evaluation 配置需要版本化。普通列表字段可以使用事件日志加快照，不必全部做事件溯源。

## 8. AI 系统设计原则

### 8.1 模型无关

后端提供统一模型接口，允许按任务选择不同供应商或模型。任务配置包含：

- 模型与版本；
- Prompt 模板版本；
- 上下文选择规则；
- 结构化输出 Schema；
- 超时、重试和降级；
- 数据保留策略；
- 单次和月度预算。

### 8.2 有根据的输出

对于知识问答、洞察和规格生成：

- 每个结论保留引用对象和原文片段；
- 区分“来源事实”“模型归纳”“模型建议”；
- 无足够证据时明确返回未知；
- 写入正式对象前提供差异预览；
- 保存用户采纳、编辑和拒绝反馈，用于评测而不是直接训练。

### 8.3 评测先于 Agent 自动化

在允许 AI 批量分类、自动建项或修改路线图前，先建立：

- 固定回归数据集；
- 任务级准确率、引用正确率和格式成功率；
- 人工评分 Rubric；
- 延迟和成本基线；
- Prompt/模型版本对比；
- 失败样本回放；
- 灰度和回滚机制。

### 8.4 成本控制

- 按工作区、用户、功能和模型统计 Token 与费用；
- 长文档先做增量索引和局部重算；
- 相同输入和配置允许安全缓存；
- 低风险任务使用低成本模型，高风险决策使用更强模型；
- 大任务异步执行，并显示阶段与可取消状态；
- 管理员可以配置预算、限额和超额策略。

## 9. 从当前代码迁移

### 阶段 A：代码基线（1–2 周）

- 确定根目录代码为唯一前端源，处理或移除重复 `src/`；
- 修复缺失的 Gemini service 和未定义变量；
- 恢复可重复的 install、typecheck、build；
- 建立环境变量、Lint、测试和 CI 基线；
- 抽离类型、日期、权限和导入导出规则；
- 记录当前 localStorage 数据格式。

完成定义：干净环境可一次安装并构建，当前核心页面可运行，用户未提交改动得到保留或明确迁移。

### 阶段 B：后端基础（2–4 周）

- 建立 monorepo 和 API 服务；
- PostgreSQL schema 与 migration；
- Workspace、User、Membership、Project、Log API；
- 会话、权限、审计和错误规范；
- OpenAPI 客户端；
- localStorage JSON 导入接口；
- 前端逐步从 localStorage 切换到 Query/API。

完成定义：项目与日志完全由服务端持久化，旧数据可迁移，权限测试通过。

### 阶段 C：协作与专业产品核心（4–6 周）

- 评论、通知、活动流和实时状态；
- Signal、Insight、Opportunity、Initiative；
- Roadmap 新视图与优先级；
- Spec 模板、版本和审批；
- 搜索和附件；
- 第一批外部分享能力。

完成定义：一个真实产品团队可以不用 JSON 文件完成从反馈到路线图和规格评审的工作。

### 阶段 D：AI 工作流（4–6 周）

- AI Gateway、Prompt 版本、结构化输出；
- 反馈摘要、聚类和洞察建议；
- PRD 草拟和一致性检查；
- 带引用的知识问答；
- AI 用量、成本、审核和评测；
- AI Lab 最小版本：Experiment、Dataset、Evaluation。

完成定义：AI 输出可追溯、可评测、可审计，并能在至少三个高频产品任务中稳定节省时间。

### 阶段 E：集成与企业能力（持续）

- GitHub、Linear/Jira、Slack/飞书；
- 发布与指标回流；
- SSO、SCIM、数据保留；
- 产品组合、组织模板和治理后台。

## 10. MVP 建议

首个可对外试用版本建议只包含以下闭环：

1. 工作区、成员、项目和权限；
2. Feedback Inbox：录入、导入、AI 摘要和人工确认；
3. Insight 与 Opportunity：证据关联和优先级；
4. Roadmap：Now/Next/Later + 时间轴；
5. Spec：模板、AI 草拟、评论和审批；
6. Delivery Link：先支持 GitHub 或 Linear 其中一个；
7. Release Review：上线指标、结论和下一步；
8. 通知、审计、搜索和数据导出；
9. AI 用量与成本基础面板。

MVP 不包含完整 AI Lab、复杂 Agent 自动化、十种第三方集成和企业 SSO。先验证团队是否愿意把真实决策和证据放进 SyncPath。

## 11. 产品指标

### 激活

- 工作区创建后 7 天内导入或创建至少 10 条 Signal；
- 至少 2 名协作者完成一次评论或评审；
- 至少一个 Opportunity 关联 3 条以上证据并进入 Roadmap。

### 核心价值

- 从原始反馈到已确认 Insight 的中位时间；
- 有证据链接的 Initiative 占比；
- 有验收标准和上线指标的 Spec 占比；
- AI 建议的采纳率、修改率、拒绝率；
- 从 Spec 承诺到 Release Review 完成的闭环率；
- 团队每周活跃协作者数，而不只看登录数。

### AI 质量

- 引用正确率；
- 结构化输出成功率；
- 人工评审通过率；
- 关键任务回归集得分；
- 每次成功任务的平均成本和延迟；
- 因 AI 错误导致的撤回或修正率。

### 商业化信号

- 工作区连续 4 周使用；
- 连接至少一个外部系统；
- 每周有跨角色协作；
- 管理者查看或分享 Roadmap/Review；
- 团队愿意为 AI 分析、权限治理或集成付费。

## 12. 商业化建议

可采用“平台席位 + AI 用量”的混合模式：

| 版本 | 目标 | 核心限制 |
|---|---|---|
| Free | 个人 PM 或小型试用 | 少量成员、项目和 AI 用量 |
| Team | 真实产品小组 | 完整闭环、基础集成和协作 |
| Business | 多团队产品组织 | Portfolio、治理、更多集成和分析 |
| Enterprise | 大型或高合规组织 | SSO/SCIM、审计、数据策略、部署选项 |

AI 功能应显示可理解的额度和成本，不使用难以预测的“无限 AI”承诺。

## 13. 关键产品原则

1. **证据优先**：任何路线图项都能回答“为什么”。
2. **人工负责**：AI 提供建议和草稿，负责人做决定。
3. **来源可见**：AI 结论显示来源、置信度和未知项。
4. **一处定义，多处呈现**：同一对象在不同角色视图复用，避免重复录入。
5. **连接专业工具**：SyncPath 管意图和上下文，外部系统管专业执行。
6. **默认可恢复**：版本、审计、撤销、归档和导出是基础能力。
7. **先闭环，再扩张**：每增加一种对象或 Agent，都必须服务完整工作闭环。

## 14. 下一步决策

在进入开发前，建议尽快确定以下五项：

1. 第一批真实试点团队规模，以及他们当前使用 Jira、Linear 还是 GitHub；
2. MVP 首个集成对象；
3. 首批 AI 功能使用哪一家或哪几家模型供应商；
4. 数据部署要求：公有 SaaS、单租户还是未来私有化；
5. SyncPath 的品牌方向和设计语言。

在这些选择尚未确定时，技术实现应保持模型无关、集成可替换、数据可导出，并优先完成 P0 和 P1 的共性能力。
