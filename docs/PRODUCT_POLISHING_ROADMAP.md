# SyncPath 产品打磨与上架路线

更新日期：2026 年 9 月 30 日。

SyncPath 的核心定位是面向 AI 产品经理及其团队的计划工具：从交付日期倒推工作，通过时间轴组织里程碑、阶段节点和执行事项，帮助团队看清计划、协同调整并跟踪落地。先把这条主流程打磨可靠，再扩展 AI 能力和商店发行。

本文接续现有产品与开发规划。下表中的后续阶段是开发安排，不代表已完成。最终优先上架 Mac、iPhone 或 iPad 仍待平台选择；本轮先完善各端可以复用的产品与服务。

## 设计原则

- 沿用灰白、深色和靛蓝品牌：Slate 50 背景、Slate 900 标题、Indigo 600 当前主要动作。
- 每个区域只突出一个主要动作；高级功能逐步展开，不用一排按钮占据主界面。
- 卡片与项目编辑使用毛玻璃弹窗，保留时间轴上下文。输入期间不抢中文输入法、方向键和 Tab 焦点。
- 三个层级表示信息粒度，不限制卡片数量。后续通过阶段分组与折叠控制复杂度，不增加一串新的优先级。
- 用户界面使用产品语言。网络和架构细节放在设置、诊断与开发文档中。
- 保存、删除、断线和权限变化必须有明确结果；界面看起来可操作的功能必须真实生效。

品牌依据见 [品牌规范](SYNCPATH_BRAND_STYLE.md)，产品方向见 [平台规划](AI_PRODUCT_TEAM_PLATFORM_PLAN.md)，技术约束见 [开发框架与验收标准](SYNCPATH_DEVELOPMENT_FRAMEWORK_ACCEPTANCE.md)。

## 第一阶段 核心流程可靠性

本轮已实现的改进：

| 范围 | 本轮结果 | 验收方式 |
|---|---|---|
| 首页与登录 | “API 模式”改为“团队计划”；去掉无功能访客入口；项目卡片可用键盘打开，按权限显示删除入口 | 登录、语言切换与首页检查 |
| 创建项目 | 居中毛玻璃弹窗、默认日期、中文名称、日期校验、保存中防重复点击、关闭草稿确认 | 从首页创建测试计划；结束日期早于开始日期时阻止提交 |
| 日历简化 | 移除中国/美国选择、节日标签和显示开关；单项目与多项目都按自然日显示；新项目默认不启用国家日历，已有字段保留兼容 | 中英文创建弹窗与两种时间轴检查；新项目默认值及旧字段兼容回归 |
| 卡片保存 | 清空概览和详情可真实保存；确认成功的写入不因后续刷新失败被误判为失败 | 浏览器清空保存后，再读取 API 返回值 |
| 多人编辑 | 草稿绑定打开时的版本；冲突后保留草稿并展示最新内容；明确确认后才替换 | 模拟另一窗口保存，再在旧编辑器保存并对照 |
| 时间轴 | 初始缩放改善可读性；选中卡片尺寸稳定；鼠标位移与日期一致；整组移动限制在项目范围内 | 几何回归和实际窗口检查 |
| 删除 | 拖出时间轴不再误删；删除选中卡片先弹出产品内确认 | 取消删除后卡片保留 |
| 同步 | 同账号不同窗口也接收卡片变化；重新连接时重新读取内容 | 事件流回归与浏览器同步检查 |
| 内网资源 | 图标随产品构建，不再依赖外部图标 CDN | 检查生产资源和界面图标 |
| 开发回归 | 自动创建临时测试数据库和独立 API，测试前核对目标，结束时清理 | 全套隔离测试、默认危险测试入口拒绝、清理检查 |

这一阶段是产品打磨的起点，还没有包含完整移动端、离线草稿恢复、撤销重做、备份恢复或商店安装包。

## 第二阶段 倒排期与计划结构

建议作为下一轮主任务。先完成“交付目标 → 阶段拆解 → 执行事项 → 调整日期”闭环。

| 功能 | 设计建议 | 验收标准 |
|---|---|---|
| 阶段分组 | 阶段包含执行事项；默认展示里程碑和阶段，按需展开事项；显示隐藏数量 | 折叠不删除数据；跨阶段移动关系与日期一致；百张卡片仍能找到目标 |
| 目标日期 | 创建计划时输入最终交付日期；阶段可标记必须达成的日期 | 调整交付日时显示受影响节点，确认后统一更新 |
| 依赖关系 | 先支持前置任务完成后开始的关系；校验环路，展示延期影响 | A 延期影响 B 有明确解释；循环依赖不能保存；只读成员不可调整 |
| 工作日排期 | 后续提供可选团队工作日历：每周工作日、公司假期、特殊工作日；统一放在设置弹窗，不恢复中国/美国二选一；计算规则统一放在 domain | 自定义工作周、假期与特殊工作日可参与倒排期；跨月、跨年、闰年有确定性测试；显示语言不改变排期规则 |
| 负责人和状态 | 负责人使用成员 ID；状态从待办、进行中到已完成；提醒与 @ 提及分开 | 撤权后不能指派；完成状态刷新仍存在；提醒不会重复产生 |
| 搜索和聚焦 | 按标题、负责人、阶段、状态筛选；定位今天、交付日、搜索结果 | 筛选不改变数据；退出筛选恢复视图；全部隐藏有明确空状态 |

框架建议：继续使用现有 React、NestJS、Prisma 和 PostgreSQL。新增阶段、依赖与负责人时，通过数据库迁移、API 契约、前端缓存和权限一起交付，不另建一套仅存在浏览器中的计划状态。批量改期采用服务端事务与版本校验，避免半个计划成功、半个失败。

## 第三阶段 团队可以每天使用

| 功能 | 交付范围 | 验收标准 |
|---|---|---|
| 邀请与权限 | 工作区/项目成员入口统一；角色说明；清楚区分项目可见性与编辑权限 | 两个独立账号完整走通邀请、查看、编辑、降权、移除；在线界面及时收敛 |
| 讨论 | 卡片评论、回复和 @ 通知；通知定位原卡片；保留已读状态 | 断线、重复请求不重复通知；失去权限后不能读取旧通知内容 |
| 撤销与历史 | 先支持移动、编辑、删除的恢复；提供变更记录和操作者 | 刷新和重新登录后仍可恢复；撤销遇到他人新版本时提示冲突 |
| 草稿恢复 | 网络失败和应用意外关闭时保留本机草稿；按账号隔离 | 断网、强制关闭、重新打开后找回草稿；切换账号不泄漏内容 |
| 入门体验 | 空时间轴直接说明如何添加；提供少量可选计划模板 | 新用户可独立创建第一份计划；模板创建失败不留半份数据 |
| 多项目视图 | 对比时加载全部选中项目数据；统一日期范围和筛选 | 未打开过的项目也能正确对比；切工作区不带入旧的选择 |

协作事件负责通知变化，数据库负责保存事实。后续部署多个 API 实例时需要跨实例事件传递；当前进程内事件流不能直接当成多实例发布方案。断线后的重新读取与写入版本校验应始终保留。

## 第四阶段 可交付安装与运行

这一阶段再集中修复桌面封装。当前 Electron 的入口位置、模块格式、生产资源路径和服务地址配置需要梳理；现有 Web 构建通过不代表桌面应用已经可用。

| 工作 | 验收标准 |
|---|---|
| 明确目标平台与客户端方案 | Mac 或移动端优先级明确；共用后端和领域规则；避免维护两套相互漂移的业务逻辑 |
| 修复桌面启动和打包 | 从干净 checkout 可生成安装包；安装后启动不依赖开发服务器；退出后无遗留进程 |
| 公司内网与托管服务连接 | 用户能理解连接到哪个团队；服务不可达时有可恢复的提示；不能把 localhost 写死进正式包 |
| 桌面基础体验 | 窗口尺寸、菜单、快捷键、通知、文件导出和系统权限在目标设备上验证 |
| 可靠运行 | 迁移、备份、恢复、监控和升级流程可重复执行；升级失败时不损坏用户计划 |
| 自动回归 | 类型检查、构建、隔离 API 测试、核心浏览器场景进入 CI；记录每版已验证与未验证范围 |

不要把“做一个桌面壳”当成商店发行完成。原生能力、连接配置、数据恢复和安装验证必须一起满足真实使用需要。

## 第五阶段 商店发行准备

提交前重新核对 Apple 最新规则。下面列出与本产品最相关的准备项，不能视为保证审核通过。

- 若先上 Mac App Store，准备应用沙盒、签名、对应开发团队和发行配置。[Apple 发行准备文档](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution)
- 产品支持注册账号，需要补应用内发起账号删除的流程，并明确处理工作区所有权及团队共享内容。[Apple 账号删除说明](https://developer.apple.com/support/offering-account-deletion-in-your-app)
- 提供隐私政策、准确的商店描述和截图；审核账号及后端服务应能让审核人员访问主要功能。[Apple 审核指南](https://developer.apple.com/app-store/review/guidelines/)
- 收费、订阅与第三方登录方案确定后，单独核对对应规则；先不把未决定的付费体系混入计划编辑流程。
- 验收门槛：目标设备的安装与升级测试通过；核心功能无占位入口；资料、数据处理流程、审核环境和签名配置齐备。

## 后续迭代记录方式

每轮只选一个清晰的用户目标，交付时记录实际行为、检查证据和仍未验证的边界。推荐顺序是：本轮可靠性 → 阶段分组与倒排期 → 团队日常协作 → 安装交付 → 商店发行。AI 排期建议和自动总结应建立在可靠的计划与权限模型上，再作为可选辅助能力加入。
