## 1. 建设目标与明确假设

### 1.1 产品目标

为 AI 产品经理及其团队提供可追溯的产品工作流：

**用户反馈 → 证据与机会 → 产品计划 → PRD 与验收条件 → AI 能力验证 → 研发交付 → 发布复盘。**

路线图保留为核心入口之一；项目日志演变为进展更新与决策记录。专业性优先体现在可靠数据、明确权限、版本追溯和跨角色协作。

要区分两类 AI：

- **团队正在研发的 AI 能力**：由产品经理定义目标行为、失败案例、质量/延迟/成本阈值，并记录验证结果。
- **SyncPath 内置助手**：帮助用户摘要、起草和检索。它的调用费用、评测结果与前一类数据分别记录。

首版包含轻量的 AI 能力验收卡和评测结果导入；完整在线模型实验、自动评测执行与 Agent 编排放到后续版本。

### 1.2 排期假设

| 项目 | 规划假设 |
|---|---|
| 试点用户 | 2–3 个 AI 产品小组，每组 5–15 人；先验证团队工作流 |
| 工程团队 | 3 名全职工程师：前端 FE、后端 BE、全栈/平台 FS |
| 配套人员 | 产品负责人 PM 约 0.5 人；设计 UX 约 0.5 人；QA 在第 5 周后约 0.5 人 |
| 计划周期 | 8 个双周迭代，共 16 周；从实际立项起算，不是日历承诺 |
| 产能口径 | 每迭代 30 工程人日 × 70% 有效产能 = 21 工程人日 |
| 初步容量 | 8 × 21 = 168 工程人日；下表安排 150 人日，保留 18 人日机动 |
| 排期精度 | 当前为粗估，任务拆细后可能波动 ±30%；设计、QA、采购和对外审批不计入工程人日 |
| 首期部署 | 单区域、多个工作区；Web、API 独立构建；暂不承诺跨地域多活 |
| 首个集成 | 默认先做外部链接；自动同步暂以 GitHub 为参考适配器，S0 按试点团队实际工具决定 |
| AI 供应商 | S0 选一家用于试点；接口保持可替换，不在此承诺某模型效果或报价 |
| 试用范围 | 受邀团队，中文优先；预留国际化键值，不同步建设所有语言 |

若只有一名全栈工程师，按同一有效产能计算，150 人日约需 43 周，另计协作角色工作与风险；应缩小范围，不能直接沿用 16 周。

### 1.3 版本边界

| 版本 | 目标时间 | 必须可用 | 暂缓 |
|---|---|---|---|
| R0 团队基础版 | 第 6 周 | 账号、工作区、成员权限、项目、日志、时间轴、数据迁移、评论与保存反馈 | AI、Discovery、复杂富文本协同 |
| R1 产品闭环内测版 | 第 12 周 | 反馈→洞察→机会→计划→PRD→验收卡→发布复盘；三项 AI 助手能力；外部任务链接 | 自动双向集成、组合规划、完整 AI Lab |
| R2 受邀试点版 | 第 16 周 | 一个自动同步适配器、路线图基线、受限分享、导出、恢复演练、性能与权限验收 | SSO/SCIM、计费、多组织组合、完整暗色主题、Electron 新功能 |
| R3 拓展版 | 试点验证后估算 | 在线评测、模型/Prompt 对比、更多集成、企业能力 | 根据真实使用重新排序 |

R0/R1 为阶段内测出口，R2 才是本计划的完整试点发布出口。未实现能力保持隐藏，不展示不能使用的导航。

字体沿用现有系统 sans 栈；正文默认 14px，元数据 12px，页面标题 28–32px。原来部分 9–10px 大字距标签只保留在少量装饰位置。中文正文和关键信息不使用过小字号。

### 3.2 信息架构落实

首版一级导航控制在“工作台 / 项目 / 反馈箱 / 搜索”四项，设置位于底部。用户进入项目后，通过概览、证据、路线图、规格与验证、交付与复盘等页签工作。AI 以对象内动作和侧栏出现。

布局建议：左导航 216–240px；中间主体；按需打开 360–440px 的详情/AI 侧栏。表格支持保存筛选、列显示、批量选择。时间轴支持列表替代视图，复杂操作保持可撤销或可恢复。

每个操作显示明确状态：本地草稿、保存中、已保存、失败待重试、版本冲突。AI 区域显示“使用了哪些资料”和“将修改哪些字段”；面向用户不暴露队列名、数据库或内部模型调用代码。

### 3.3 品牌验收（BR）

- BR-01：本文 token 均进入共享 UI 包；前端与规划图采用一致主色。
- BR-02：普通正文对比度 ≥4.5:1；关键焦点/控件边界 ≥3:1；颜色不是唯一状态提示。
- BR-03：1440×900、1280×800 下核心操作无意外横向溢出；390×844 支持阅读、评论和列表替代。
- BR-04：键盘可完成登录、建项、筛选、评审；Dialog 焦点可进入、限制、退出并恢复。
- BR-05：加载、空、失败、无权限、保存和冲突状态都有可操作说明；不得用永久 loading 掩盖失败。
- BR-06：生成的架构 HTML 通过可访问 SVG 检查、字体/颜色检查与截图检查。此项本轮已检查；BR-01～05 是未来产品验收。

## 4. 框架选型与工程边界

### 4.1 推荐方案

先建立一个模块化后端和一个可独立运行的 Worker。相同仓库内共享契约，前后端独立部署。开发阶段逐步接入基础设施。

| 层 | 默认选型 | 采用理由 | 约束 / 何时调整 |
|---|---|---|---|
| 工作区 | npm workspaces | 沿用现有 npm 锁文件习惯 | 不同时维护 npm/pnpm 双锁；规模扩大再评估编排工具 |
| Web | React + Vite + TypeScript | 复用已有组件与 SPA 交互 | 基线恢复和大版本升级分开提交；上线版本在 S0 冻结 |
| 路由 | TanStack Router | 项目、筛选、对象详情可以深链访问 | URL 保存可分享视图，临时草稿不塞进 URL |
| 请求缓存 | TanStack Query | 管理服务端数据、失效与重取 | query key 包含 workspace；退出和切换身份清缓存 |
| 表单/本地状态 | React Hook Form + Zod；必要时 Zustand | 表单校验与时间轴局部交互清晰 | Zustand 不复制完整服务端对象树 |
| UI | Tailwind + Radix 基础组件 + 自有 token | 延续品牌且具备可访问交互基础 | 样式构建进入项目，去掉运行时 Tailwind CDN |
| 文档编辑 | MVP 结构化字段 + Markdown | 快速实现版本、审阅、差异 | 需要块编辑时再评估 Tiptap；实时逐字协作后置 |
| 服务端 | NestJS + Fastify + TypeScript | 模块、Guard、依赖注入和 API 契约适合团队维护 | 会话、上传、CSRF 组件使用 Fastify 兼容实现 |
| 数据契约 | REST /api/v1 + OpenAPI | 前后端解耦并能接外部工具 | 后端 DTO 为事实源，生成前端 client；不手写重复接口 |
| 数据库 | PostgreSQL | 关系、版本、事务、审计、Outbox | 不将全部业务继续存成 AppState JSON |
| ORM | Prisma，迁移 SQL 纳入版本库 | 默认选定一种，降低早期决策成本 | RLS、复杂索引仍显式 SQL；事务上下文需验收 |
| 异步 | Redis + BullMQ + 独立 Worker | 导入、AI、导出、Webhook 同步 | DB 存任务事实；队列丢失可从 DB 补偿 |
| 文件 | S3 兼容存储 | 附件、导入源与导出文件 | 私有桶；敏感下载经鉴权；本地用兼容测试服务 |
| 实时 | 服务端 WebSocket 事件 + Query 失效 | 协作通知与在线状态 | 业务写入走 API；不广播全量数据；CRDT 按需后置 |
| 搜索 | MVP PostgreSQL 关键词/标题检索；后续 pgvector | 先验证权限与召回，再加语义搜索 | 中文首版采用明确的子串/字段匹配，不能假定内置分词已解决中文检索 |
| 测试 | Vitest、API 集成测试、Playwright、k6 | 覆盖业务规则、真实 DB、用户流程和容量 | 权限/RLS/并发不可只用 mock |
| 运行 | 容器 + 同源反向代理；数据库优先托管 | 易于部署和恢复 | Kubernetes、微服务、多活暂不引入 |

NestJS 官方支持 Fastify 适配，但 Express 专用中间件不能自动沿用；应在第一个迭代验证会话和上传方案。[官方说明](https://docs.nestjs.com/techniques/performance)

OpenAPI 用于生成接口描述；建议进一步生成客户端并在 CI 检查漂移。[NestJS OpenAPI](https://docs.nestjs.com/openapi/introduction) TanStack Query 负责服务端状态缓存，UI 状态仍由本地管理。[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview)

### 4.2 备选与暂不采用

| 选择 | 本次建议 | 重新评估条件 |
|---|---|---|
| Next.js 全栈 | 当前交互型 SPA 保持 React/Vite；营销站可独立 | 确有公开内容 SEO/SSR 需求 |
| FastAPI | Python 可用于未来专门评测 Worker | 团队明显偏 Python，且有大量 Python 评测代码 |
| Supabase 等托管后端 | 可使用托管 PostgreSQL/Auth 加速试点，但须重新核定边界 | 极小团队愿意接受平台依赖；业务授权仍必须统一 |
| GraphQL / tRPC | MVP 采用 REST/OpenAPI | 多客户端复杂查询成为真实瓶颈 |
| 独立向量库 / Elasticsearch | 首期不引入 | 权限过滤、中文召回或规模基准证明 PostgreSQL 不满足 |
| Yjs 富文本协作 | 保留技术选择，先实现文档级版本冲突 | 两人同时逐字编辑确有高频需求 |
| 全新 Electron | Web 试点稳定后再规划 | 离线、桌面集成、通知需求得到验证 |

### 4.3 目标代码组织

~~~text
apps/
  web/src/
    app/                    路由、Provider、页面框架
    features/
      workspace/ projects/ roadmap/ discovery/
      specifications/ validation/ delivery/ assistant/
    shared/                 客户端权限提示、日期、格式化
  api/src/
    modules/
      identity/ tenancy/ projects/ planning/
      discovery/ specifications/ validation/ delivery/
      collaboration/ ai/ integrations/ audit/
  worker/src/
    processors/             AI、导入、导出、同步、通知
packages/
  domain/                   纯业务规则；无浏览器/Nest/ORM 依赖
  backend/                  应用服务、数据库、授权、审计；仅 API/Worker 使用
  contracts/                OpenAPI 和事件协议
  api-client/               生成代码；Web 使用
  ui/                       设计 token 与基础组件
  config/                   TS、lint、测试配置
infra/                      本地 Compose、部署模板、备份脚本
docs/                       ADR、Runbook、验收证据
~~~

依赖方向：Web → api-client / ui；API 和 Worker → backend → domain。Web 不得导入数据库客户端、后端密钥或 Prisma 模型。服务端跨模块通过公开应用服务或事件交互，不直接更新其他模块的表。

### 4.4 运行与环境

- 开发环境：一个 workspace 命令启动 Web/API，Compose 提供 PostgreSQL；S3/Redis 在相关迭代接入。
- 预发布：独立数据库、独立模型密钥、测试通知通道、测试数据；禁止连接生产账号。
- 生产：同一域名下静态 Web + /api + /events 代理，Web/API/Worker 可独立更新。
- 会话 cookie 使用 HttpOnly、Secure 和合适的 SameSite；写请求校验 CSRF/Origin；开发跨域仅白名单。
- 使用服务器会话与成熟密码哈希库；会话标识不放 localStorage，模型密钥只在服务端。
- 数据库迁移由单独部署步骤执行；采用先扩展再切换再删除的兼容式迁移。
- 结构化日志串联 request_id、task_id、workspace_id；正文/凭据默认脱敏。审计与诊断日志分开管理。
- DB、附件均备份；至少每个 R2 候选版本执行一次隔离恢复演练。

## 5. 领域模型与业务状态

### 5.1 必备对象

| 对象 | 关键字段 / 关系 | 首次阶段 |
|---|---|---|
| User / Session | 全局账号；验证状态；会话失效时间 | R0 |
| Workspace / Membership | workspace_id、user_id、role、status | R0 |
| Project / ProjectMember | name、owner、日期、时区、可见性、成员权限 | R0 |
| ProgressEntry | project_id、title、level、entry_date、summary、notes、legacy_id、revision | R0 |
| Initiative / Dependency | 负责人、目标、状态、计划区间、优先级及依赖 | R0 基础；R1 关联证据 |
| Signal / SourceRevision | 来源、原文、客户/角色标签、采集时间、内容版本 | R1 |
| Insight / EvidenceLink | 结论、支持/反对证据、来源版本、引用片段 | R1 |
| Opportunity | 问题、目标用户、验证状态、价值评分及依据 | R1 |
| Spec / SpecRevision / Approval | 计划项、结构化 PRD、不可变版本、审核策略与决定 | R1 |
| Capability / ValidationRecord | 正在研发的 AI 能力、指标定义、阈值、样本版本、评测报告 | R1 轻量 |
| Release / Review / MetricSnapshot | 发布范围、观察窗口、目标/基线/实测、复盘结论 | R1 |
| ExternalLink / IntegrationEvent | 外部对象 ID、同步方向、状态、最后成功时间 | R1 链接；R2 同步 |
| Comment / Notification / AuditEvent | 对象关系、操作者、当前权限范围与事件版本 | 分阶段 |
| AITask / AIAttempt / AIProposal | 状态、输入版本、权限来源、生成结果、采纳目标版本 | R1 |
| BudgetReservation / UsageEntry | 预占、调用尝试、计价版本、估算/实际费用 | R1 |
| ImportBatch / ImportItem / Outbox | 批次状态、旧新 ID、校验报告、待发布事件 | R0 起 |

约束：

- 业务对象都带 workspace_id；项目内数据同时带 project_id。User 是全局身份例外，不能把“每张表一个 workspace_id”机械套到所有基础表。
- 项目对象的外键包含租户范围，阻止把工作区 A 的 Spec 关联到 B 的 Initiative。
- 文档内容可用有 schema_version 的 JSONB；用户、权限、引用、审批、状态、索引字段关系化。
- 业务“日期”使用 DATE；事件“时刻”使用 UTC timestamptz；展示时按用户时区转换。
- 客户原话、模型归纳、人工决定分别记录。来源删除/撤权会影响关联衍生内容的可访问性。
- 项目、任务和卡片删除后不可恢复；直接清除数据库记录与关联权限、通知、分享和历史副本。未来新增附件、搜索索引或 AI 派生数据时，删除必须同步处理这些副本与缓存。

### 5.2 状态机与不可变版本

| 对象 | 允许主路径 | 规则 |
|---|---|---|
| Opportunity | captured → validating → validated → committed / rejected → archived | committed 要关联 Initiative；重新打开保留理由 |
| Initiative | planned → active → in_review → done；可 blocked / cancelled | done 要有负责人确认和验收结果；延期不自动调整依赖项 |
| Spec | draft → in_review → approved → superseded / archived | 修改已提交内容生成新 revision，旧批准不能覆盖新版 |
| Release | draft → ready → released → reviewed / rolled_back | AI 能力未达阈值不能自动判定 ready；例外需有负责人和理由 |
| ImportBatch | uploaded → validated → applying → completed / failed / cancelled | 正式写入批次原子提交；失败重试不新增重复记录 |
| AITask | queued → running → succeeded / failed / cancelled / needs_reconciliation | succeeded 只表示草稿生成成功；结果未知需核对 |
| AIProposal | draft → accepted / rejected / stale | 接受时再校验目标 revision 与当前权限 |

审批策略首期每份 Spec 指定一名审核人。多级审批、会签和流程设计器后置。审计不可通过普通内容编辑覆盖；修改内容与撤销决定均创建新记录。

### 5.3 MVP 的 AI 能力验收卡

每个 AI Initiative 可关联一张卡，至少记录：

1. 用户任务和期望输出，明确失败时用户如何继续。
2. 候选模型/Prompt/知识源版本，外部实验或仓库链接。
3. 样本集版本、数量、覆盖场景；原始样本权限。
4. 质量、延迟和成本阈值，指标单位、分母、测量窗口和来源。
5. 结果导入、失败案例、审核结论与责任人。
6. 发布时采用的版本和回退条件。

首期可手工填写或导入 CSV/JSON 结果，不建设通用执行引擎。这样 R1 已能服务 AI 产品团队，同时控制研发范围。

## 6. API、并发和可靠性契约

### 6.1 API 约定与主要端点

统一约定：UUID 标识；分页使用 cursor；日期 ISO 格式；非法字段白名单校验；错误携带稳定 code、message、requestId 和可公开的字段详情。

| 端点示例 | 含义 | 关键契约 |
|---|---|---|
| POST /api/v1/sessions | 登录 | 建会话 cookie；限流；不返回密码 |
| GET /api/v1/workspaces/{wid}/projects | 项目列表 | 先授权，再分页；计数同样过滤 |
| PATCH .../projects/{pid}/initiatives/{id} | 修改计划项 | 必须带 expectedRevision；冲突返回 409 |
| POST .../imports/validate | 导入预检 | 返回字段错误、统计、内容摘要和目标映射 |
| POST .../imports/{id}/apply | 执行导入 | 幂等键 + 已验证文件 hash；调用者可创建目标对象 |
| POST .../specs/{id}/submit | 发起评审 | 绑定不可变 revision 和 reviewer |
| POST .../specs/{id}/approvals | 审核 | 审核人和当前待审 revision 匹配 |
| POST .../ai/tasks | AI 任务 | 202 + taskId；先授权与预占预算 |
| POST .../ai/proposals/{id}/accept | 采纳建议 | 差异预览、expectedRevision、引用再次校验 |
| POST .../capabilities/{id}/validation-records | 记录验证 | 样本/配置/指标版本齐全 |
| POST .../releases/{id}/reviews | 上线复盘 | 观察期、指标快照与后续动作 |
| GET /api/v1/events | WebSocket 握手/订阅入口 | cookie 会话、Origin 与订阅对象授权 |

错误语义：未登录 401；可见对象但无写权限 403；不可见/不存在对象统一 404；字段错误 422；版本冲突 409；限流 429。日志可以保留更详细原因，响应不得泄露私有对象名称。

### 6.2 乐观锁

用户编辑时记录 revision。服务端按 id + workspace_id + revision 条件更新，并将 revision 加一；受影响行数为零时在鉴权后返回 409 和最新版本。

客户端收到冲突时保留草稿，展示差异，允许重新应用。撤销也作为有基线的新命令执行；不能用历史 AppState 覆盖其他成员之后的修改。

### 6.3 实时协作

- 业务事务提交成功才发送 object.changed 事件；载荷以对象 ID、revision、eventId 为主。
- Web 根据事件失效对应 Query 并重新获取；网络中断恢复后重新拉取，不依赖事件绝不丢失。
- Presence 只显示谁正在查看/编辑，不代表写权限和排他锁。
- 离线只保留本人草稿；恢复后按版本冲突流程提交。
- R0 可以先实现保存后同步与重取；服务端推送在协作任务内补齐。字级 CRDT 为 R3 单独设计。

### 6.4 异步任务与 Outbox

业务修改、审计摘要和 Outbox 在同一 DB 事务提交。Relay 将事件投递到 BullMQ；Worker 使用逻辑任务 ID + 操作类型去重，数据库唯一约束保证业务结果只生效一次。

队列按至少一次投递设计；重试不能等于业务重复执行。[BullMQ 幂等任务建议](https://docs.bullmq.io/patterns/idempotent-jobs)

- 入队、执行开始、结果读取、采纳分别检查当前权限。
- 重试采用有上限的退避；永久错误进入 failed 并给出可操作原因。
- 已取消任务的迟到回调不能改回 succeeded。
- 外部模型调用可能在超时前已被执行，不能承诺外部费用 exactly-once。
- 结果未知时保存 needs_reconciliation，使用供应商幂等/查询能力或人工核对；禁止自动无限重试。
- 模型输出通过 schema 和引用检查后存为 AIProposal。正式对象由采纳接口写入。

### 6.5 成本与预算

AITask 表示一个用户意图，AIAttempt 表示一次供应商调用，UsageEntry 表示一次费用记录，不能合成一个字段。

调用前在事务内预占估算上限，并限制上下文和最大输出。只有支持明确费用上界的调用才能进入严格硬预算通道。调用后释放剩余额度并结算；估算、实际、未知费用分别标记。

“已结算 + 未结算预占不超过上限”是内部准入约束，不能承诺供应商迟到补账绝不超出；补账通过调整记录体现并暂停新任务，管理员可核对原因。价格带版本与币种，禁止用今天价格重算历史账单。

## 7. 权限、检索和数据迁移

### 7.1 授权模型

MVP 工作区角色 Owner / Admin / Member；项目角色 Lead / Editor / Viewer；Guest 只能访问显式分配项目且默认只读。审核人是 Spec 上的职责，不把所有审批能力隐含赋予 Admin。

Owner/Admin 可管理成员，但普通业务访问仍要求项目授权；特权支持访问未来通过单独审计流程实施。

每条请求验证“身份有效 → 工作区成员 → 项目可见 → 操作允许 → 对象状态允许”。workspace_id 不从客户端直接信任，而是在会话和成员关系中验证。

数据层使用租户字段和组合约束；RLS 为第二层保护。运行账号不使用 superuser/BYPASSRLS，不拥有业务表；迁移账号分离；租户上下文使用事务内 SET LOCAL 或等效机制，连接池复用必须有隔离测试。RLS 默认行为和表所有者绕过规则见 [PostgreSQL 官方文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)。

### 7.2 撤权与 AI 衍生内容

- 新请求在权限事务提交后即按新权限判定；在途操作在受保护写入/结果发布前复核。
- WebSocket 收到撤权后关闭相关订阅，客户端清除 Query 与页面内容；目标为 ≤5 秒，离线客户端下次连接必检查。
- 检索先限制允许的数据范围，汇总、结果计数、引用、附件下载和通知遵守相同规则。
- AI 结果保存来源 ID、revision 和权限依赖。读取结果正文时再校验全部受保护来源；不能只隐藏引用链接。
- 采纳后的文档也保留来源权限依赖；默认有效读者是目标对象与受保护来源读者的交集。不能把私有项目资料摘要后发布到更宽范围来绕过权限。MVP 不提供自动解除该依赖的功能。
- 撤权后排队任务停止后续受保护操作；已发给供应商的请求不能承诺撤回，按取消/结果隐藏规则处理。
- 管理员撤销分享后，新访问拒绝。敏感文件下载通过鉴权代理；已下载/截图内容不宣称可远程抹除。
- AI 提示词中的外部文档是资料，不是权限指令；不得因文档要求自动调用未授权工具。

### 7.3 旧数据迁移映射

| 旧字段 / 行为 | 新位置 | 规则 |
|---|---|---|
| projects[] | Project | 旧 ID 保留在 legacy_id；服务端生成新 UUID |
| personnel 字符串 | legacy_personnel / 团队说明 | 不用子串匹配授予任何账号权限 |
| logs[project][date][] | ProgressEntry | 日期保留为 DATE；原分组信息可追溯 |
| WorkLog.author | title | 实际代表目标标题；不映射为用户身份 |
| goals[] | 进展条目内的 legacyGoals JSON | 首期保真，不静默丢弃；后续再显式迁为验收清单 |
| createdAt / updatedAt | legacy 时间戳 + 合法业务时间 | 非法值进入预检错误，不伪造精确时间 |
| currentUser.password / 本地角色 | 不导入 | 新账号注册或邀请；旧角色不授予服务端权限 |
| readonlyProjectIds | 导入参考信息 | 显示给导入者确认；服务端重新设置权限 |
| 撤销历史 / selectedProjectId / view | 不作为业务数据迁移 | UI 偏好按用户新建 |
| 房间关闭时删除/只读逻辑 | 历史说明 | 新系统以项目权限和明确的永久删除操作决定数据生命周期，成员离线不删数据 |

迁移 Runbook：

1. 用户主动导出当前浏览器 JSON；提示数据来自当前设备与浏览器，不自动发现其他电脑的数据。
2. 本地原数据不修改；清除密码字段后形成导入上传文件。服务器亦做白名单并拒绝敏感凭据字段。
3. 解析 schema、验证日期/长度/重复 ID/孤立日志，生成 hash、统计和旧新 ID 映射预览。
4. 选择目标工作区和项目所有权；不凭相同 username 自动认领他人记录。
5. 相同目标工作区 + source hash + schema version 为同一幂等批次。首期建议限制 10MB / 10,000 条日志，超过则提示拆分。
6. 预检全通过后在事务中正式写入；不让半成品出现在普通业务查询中。
7. 对账项目数、日志数、日期、goals、标题、锁定状态和随机内容 hash，报告成功/失败/跳过。
8. 用户确认后切换 API 数据源；迁移过程中避免旧端和新端同时编辑同一数据。
9. 失败时保留原文件与错误报告；成功批次的后续用户编辑不可通过简单整批删除回退。恢复采用变更记录核对与受控补偿。

先裁多语言、完整暗色、额外模板、精美报表；再裁路线图基线和外部分享；自动集成可降为手动链接，但 R2 必须改名为“未接入自动同步的试点版本”并列明未交付项。

权限、迁移对账、对象版本、AI 来源校验、成本边界和恢复能力不能为了准时而跳过。若这些超预算，调整发布日或缩小试点，不能用前端提示代替后端实现。

## 9. 详细验收用例

以下均为未来执行计划。除 BR-06 的文档架构图检查外，本轮没有实施这些业务能力，没有任何 AC 被标记为通过。

### 9.1 数据与环境

- 功能数据集 F1：工作区 A/B；各有 Owner、Member；A 含项目 P1/P2、Editor/Viewer 及只可访问 P1 的 Guest。
- F1 含至少 100 条 Signal、10 个 Initiative、3 份 PRD、2 张 Capability 卡、2 次 Release 和一份混合正常/异常的旧版导出。
- AI 数据集 E1：100 个冻结任务，40 摘要、30 PRD、30 证据问答；三组均含正常、缺证据、越权、伪造引用或冲突情况，并标注期望行为。
- 性能数据集 P1：10 个工作区，合计 10,000 条 Signal、200 个计划项；固定种子，保证冷热缓存和权限范围可重现。
- 外部集成使用专用测试账号；正常 CI 使用模拟供应商。真实付费 AI 验收在已授权预算内运行并记录实际费用。

### 9.2 账号、数据与协作

| ID | 操作 | 明确通过条件 |
|---|---|---|
| AC-01 | 浏览器甲注册建工作区，乙登录；退出后重放旧会话 | 两端读取相同服务端数据；旧会话返回 401；旧本地密码/角色未作为服务端凭据 |
| AC-02 | A 用户替换详情、写入、搜索、计数、导出中的 ID 为 B 的 | 不可见对象统一 404；响应、摘要、计数、导出无 B 内容；DB 未改变 |

| AC-04 | 用户正查看对象、搜索和 AI 结果时撤权，再刷新/保存/下载 | 新服务端操作拒绝；在线客户端 ≤5 秒收敛并清缓存；AI 正文按来源权限封闭；离线重连必拒绝 |
| AC-05 | 打开只读路线图分享，尝试读取 PRD/原始反馈，再撤销链接 | 只显示明确分享字段；关联 ID 不能读内部对象；撤销后拒绝；下载边界被记录 |

| AC-10 | 两人从 v1 修改同一计划日期 | 首次保存得 v2，第二次 409；界面保留后者草稿并显示冲突；没有静默覆盖 |
| AC-11 | 建 A→B→C 再加 C→A，随后移动 A | 循环依赖拒绝；展示可见范围内受影响项；不自动改其他项目日期 |
| AC-12 | 建基线后修改日期/负责人/状态，再恢复单项 | 基线不变；差异可读；恢复创建新 revision 与审计，不能擦除历史 |
| AC-13 | PRD v1 交指定审核人批准；另一 Editor 调用批准/发布接口 | 仅指定审核人可批准；发布遵守状态与角色；批准绑定 v1 |

| AC-16 | 一端离线草拟，另一端保存，再恢复/重连/刷新 | DB 版本一致；旧草稿可恢复，冲突按 AC-10；重复事件无重复作用，缺事件可重取 |

### 9.3 AI、集成和运行

| ID | 操作 | 明确通过条件 |
|---|---|---|
| AC-17 | 三条信号生成洞察后修改一条原文 | 结论可定位 source ID/revision/片段/task；标明来源已更新；事实、归纳与建议分开 |
| AC-18 | 无证据问题；伪造引用 ID 或不匹配片段 | 返回缺证据或明确推断；伪造引用被拒绝；不写入正式 Insight/Spec |
| AC-19 | AI 排队后、执行中、采纳前分别撤权 | 各阶段按当前权限复核；停止后续受保护操作；结果不向撤权用户返回；不承诺撤回已发出的模型请求 |
| AC-20 | 人工改 PRD 后采纳基于旧版的 AI 草稿，再测试拒绝 | 显示差异并处理 stale/409；拒绝不改正式内容；采纳记录人、任务和版本 |
| AC-21 | 固定 E1 对比候选 Prompt/model 与基线；含越权与伪造引用 | 保存配置/样本/结果；越权泄露 0；伪造引用 fixture 全拦截；满足下文质量门槛 |
| AC-22 | 同一任务重投 3 次，在 DB 提交后、队列确认前终止 Worker | 只有一个逻辑业务结果；重启可恢复；外部真实调用尝试单独记账 |
| AC-23 | 排队、执行、落库边界取消，再投递迟到回调 | 取消不回变成功；不写正式目标；已产生费用如实记录；残留产物按策略清理 |
| AC-24 | 同一 Webhook 重放 3 次，新旧事件倒序，再发错误签名 | 只处理一次；旧事件不回退状态；错误签名拒绝；失败可重放；不自动覆盖未映射字段 |
| AC-25 | 余额够 2 个有确定上限的任务，同时提交 10 个 | 原子预占最多接纳 2 个；其他明确额度不足；不同成员不能突破工作区准入预算 |
| AC-26 | 模拟供应商可能已执行的超时，以及明确未发送的失败 | 前者核对/幂等查询，后者有限重试；不无限重复；每次尝试有费用状态与记录 |
| AC-27 | 用固定价格/token fixture 跑成功、失败、取消、重试及补账 | 聚合与明细一致；估算/实际区分；补账追加而不改写历史价格；未知费用可见 |
| AC-28 | 隔离环境恢复数据库与附件，模拟主库丢失 | RPO ≤24h，RTO ≤4h；对象/附件 hash、关系和租户权限通过；有时间线和差异报告 |
| AC-29 | 发布 schema 变更后模拟健康检查失败并回退应用 | 旧应用在兼容窗口可运行；新数据保留；不能靠清库完成回退；Runbook 可执行 |
| AC-30 | 固定 P1 数据和设备，50 活跃虚拟用户压测 15 分钟，执行核心 UI | 满足第 10 节容量目标并附硬件、网络、数据和版本；不混入供应商模型耗时 |

### 9.4 产品闭环补充检查

- PC-01：从一条原始反馈可导航到 Insight、Opportunity、Initiative、Spec 和 Release；反向导航能返回原文。每一跳检查权限。
- PC-02：支持证据与反对证据可同时关联；AI 不自动删除反证；评分可展开计算因素与人工调整理由。
- PC-03：PRD 至少有问题、目标/非目标、流程、异常处理、验收条件和指标；缺必填项不能提交审核。
- PC-04：AI 验收卡区分产品质量、时延、成本；结果报告有样本版本、分母、配置版本、日期和审核人；导入异常逐行显示。
- PC-05：低于团队设定阈值的能力不能自动标记验收通过；人工例外必须显式记录风险、责任人和理由。
- PC-06：发布复盘展示目标、基线、实际和观察窗口；没有数据时显示“未采集”，不能当作 0 或达标。
- PC-07：工程系统任务标为 Done 只更新交付状态，不自动把产品结果标为成功。
- PC-08：成员离线或退出协作，不删除项目；Owner 移除成员后项目与审计仍保留。

## 10. 非功能与 AI 质量门槛

以下是试点建议目标。S0 冻结环境，S5 冻结 AI 数据集和模型配置；调整目标须记录理由。百分比不等同对未知真实数据的保证。

### 10.1 测量环境与性能

建议基准：API/Worker 各 2 vCPU / 4GB；PostgreSQL 2 vCPU / 4GB；Redis 1GB；同区域；浏览器使用 1440×900、记录机型/Chrome 版本，20Mbps、100ms RTT。与生产不同的部分必须在报告里标明。

| 项目 | 验收目标 | 口径 |
|---|---|---|
| 普通 API | p95 ≤500ms；服务端错误率 <1% | 50 活跃用户，80% 读/20% 写，每用户约每 2 秒操作，15 分钟；预期 401/403 不算服务错误 |
| 异步接单 | p95 ≤1s | 只测校验/预占/创建 task，生成耗时另列 |
| 核心首屏 | 可操作 ≤3s | 冷启动 20 次 p95；登录/项目/路线图分别测 |
| 路线图 | 200 项下拖动反馈 p95 ≤100ms | 固定脚本采样；滚动虚拟化；不只写“流畅” |
| 对象事件 | 提交后另一在线客户端可见 p95 ≤2s | 记录提交、收到、渲染时间；20 次以上 |
| 撤权 | 新请求立即按新权限；在线 UI 清理 ≤5s | ACL 事务提交为起点；最终写入/返回前再次鉴权 |
| 恢复 | RPO ≤24h，RTO ≤4h | 包含附件；从宣布恢复开始至核心流程可用结束 |
| 试点可用性 | 99.5% 月度运行目标 | 需要完整观测周期；上线前只能验证监控与故障恢复，不能预先宣称达到 |

AI 完成耗时按任务分别统计；建议摘要 p95 ≤30s、PRD 草稿 p95 ≤90s 作为初始体验目标，前提是冻结输入上限、模型和供应商区域。超时展示可恢复状态，不伪装成功。

### 10.2 内置助手的质量评测

| 指标 | 建议门槛 | 分母与判定 |
|---|---|---|
| 权限泄露 | 0 | E1 越权样本及 AC-19 不得输出受保护事实/片段；任何一次阻断发布 |
| 引用可核验率 | ≥95% | 所有实际展示的事实引用中，ID、版本、片段和支持关系均正确；记录引用总数 |
| 伪造引用拦截 | 100% fixture 通过 | 不存在 ID、错版本、片段不匹配三类都测试 |
| 结构化输出成功率 | ≥99/100 | E1 的 100 次任务，经最多 1 次格式修复后；同时报告首轮成功率、重试数与额外成本 |
| 人工任务通过率 | ≥85/100 | 两名审核人依据事实一致、覆盖要点、可操作、无虚构逐项评分；分歧保留并裁定 |
| 缺证据处理 | 对缺证据 fixture 全部显式提示 | 不允许为追求完成率而自动补出“事实” |
| 成本 | 不超过 S0 设定的任务/工作区预算 | 固定模型价格版本、输入/输出上限；真实 token 与估算分别记录 |

结构化的“证据不足/无权限”响应可以是正确任务结果，按样本期望判定；不得将困难样本从分母移除。引用正确率需要人工检查“来源是否支持结论”，仅验证 ID 存在和片段匹配不够。

内置助手评测与用户自己产品的 ValidationRecord 分表、分权限、分指标口径。团队产品的质量阈值由该产品负责人定义，不把 SyncPath 的 95% 引用指标生搬给所有 AI 产品。

## 11. 测试、交付和发布签收

### 11.1 测试分层

- 单元：日期、优先级计算、状态转换、费用计算、旧字段映射。
- API + 真实 PostgreSQL：租户/RLS、事务、幂等、revision、审批、导入对账。
- Worker：DB 提交后崩溃、重复投递、撤权、超时未知、取消、预算争抢。
- 契约：OpenAPI 更新生成 client 后无漂移；事件 schema 兼容，Web 不依赖后端私有字段。
- E2E：两账号两浏览器协作，导入，证据链，PRD 审核，AI 草稿采纳和发布复盘。
- 手工 UAT：真实 PM、研发、算法成员分别执行各自任务，记录完成时间和阻碍。

### 11.2 计划中的 CI 命令

下列是 DEV-002 要建立的命令契约，当前仓库尚未提供这些全部脚本：

~~~text
npm ci
npm run lint
npm run typecheck
npm run test:unit
npm run test:integration
npm run contracts:check
npm run build
npm run test:e2e
~~~

部署候选版增加 test:ai-regression、test:load、backup:verify 和 restore:rehearse。付费供应商回归不在普通 PR 中自动反复触发，使用冻结 fixture 与独立预算门禁任务。

### 11.3 完成定义

每个开发任务必须同时满足：

1. 业务行为存在，API、UI 和数据迁移完整；不存在只接通按钮却依赖假数据的“完成”。
2. 有对应需求/DEV/AC 编号；正向、异常、越权和冲突场景按风险覆盖。
3. 测试与 UI 状态检查通过；失败已修复或明确列为未交付，不能标为通过。
4. 新配置有示例、默认行为和缺失提示；新增数据变化有 migration。
5. 运行日志可定位，用户错误能理解，凭据不进入客户端和日志。
6. 变更可回退或恢复；数据相关变更有迁移/恢复记录。
7. 产品负责人确认行为，QA 确认用例，技术负责人确认接口与发布条件。

### 11.5 发布阻断与回退

越权泄露、数据丢失/重复、静默覆盖、审批绕过、无界费用、恢复失败为硬阻断。其余缺陷按影响分级，核心流程阻塞未清零不得发布；非核心视觉问题可记录负责人和修复版本。

发布顺序：预发布验收 → 备份/兼容迁移 → 健康检查 → 内部工作区灰度 → 两个受邀团队 → 观察 48 小时。检查错误率、同步、导入与 AI 费用异常。触发回退时先关闭相应 feature flag/Worker 消费，再回退应用；不要删除已新增的业务数据。

## 13. 拓展阶段建议

R2 后先观察至少四周：团队是否持续录入证据，PRD 是否真正被研发使用，AI 建议采纳后的返工情况，评测卡是否影响上线决定，用户是否能在五分钟内回答“这个功能为什么做”。

优先拓展三个方向：

1. AI Lab：可复现实验、数据集切分、人评队列、模型/Prompt/检索配置对比、回归与线上反馈回流。先接已有评测工具，避免重造训练平台。
2. 团队效率：会议行动项、依赖风险、周报草稿、反馈重复识别。自动写入范围逐动作授权并审计。
3. 企业能力：SSO/SCIM、数据保留、审计导出、产品组合、指定区域与私有化。只有明确客户和维护预算时进入交付计划。

商业化设计可沿用席位 + AI 用量，但收费、支付、套餐和企业协议不进入上述 16 周工程范围。先验证“证据—决策—验证—结果”的实际使用。
